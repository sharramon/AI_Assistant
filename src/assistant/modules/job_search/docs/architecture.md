# job_search: architecture

## Interface

| | |
|---|---|
| Tools | `job.search(days)`: answers at once; the result reaches the caller as an [`AgentNotice`](../../../../../docs/api/agents.md#agentnotice) at its next turn. A **stub** today: the notice says the runner isn't built. `job.open_ui()`: opens the job UI in its own window on the Tracker, every time: starts the server first if it isn't answering, closes the job UI window already open, then opens a fresh one, so there's only ever one; gives `{url, launched, window}`, or `not_available` if it can't start |
| Handles | nothing: the agent is called through `ITaskAgent`, the menu through `InvokeTool` |
| Calls | [`ctx.permissions.request_set`](../../../../../docs/api/modules.md#modulecontextpermissions) on start (through [`request_access`](../../../../../docs/api/infra.md#agent_access)); [`ReportTask`](../../../../../docs/api/agents.md#reporttask); [`DeliverMessage`](../../../../../docs/api/agents.md#delivermessage) to its own agent (cv's events); the [Hub's menu](../../../../../docs/api/agents.md#the-hubs-menu) through the door, as `job_search_agent`; [`IAgentNames`](../../../../../docs/api/agents.md#iagentnames) (`ProfileAgent` claims the id on start, releases it on stop) |
| Publishes | [`AgentActivity`](../../../../../docs/api/agents.md#agentactivity), [`AgentStateChanged`](../../../../../docs/api/agents.md#agentstatechanged), [`SessionUsage`](../../../../../docs/api/agents.md#sessionusage), [`PermissionModeChanged`](../../../../../docs/api/agents.md#permissionmodechanged), [`AgentNotice`](../../../../../docs/api/agents.md#agentnotice) |
| Listens to | [`ResetRequested`](../../../../../docs/api/agents.md#resetrequested) (for the job agent). cv's named events ([`ModuleEvent`](../../../../../docs/api/messaging.md#moduleevent)) `cv.job_finished` and `cv.job_submitted`: one whose `reply_to` is its agent becomes one `DeliverMessage` waking it (`cv_finished_text`: the job, the folder, cv's one-line summary, "update this job's row in the tracker", `cv.read_result task_id=…`; `cv_submitted_text`: cv's summary, the folder, the tracker row, carry on). The agent updates the tracker; the module writes nothing into the job project. An event published while job_search is off or reloading, or across an app restart, is lost (the bus keeps nothing); that's accepted, with no fallback ([decisions](../../../../../docs/architecture/decisions.md#decided), 2026-11-13) |

## Owns and launches

- **Its access, asked for on start:** `start` asks for the whole list in one request (`request_access`, subject `job_search_agent`). If the saved grant matches the list, the agent is built at once. Otherwise a card opens and the start ends with `AccessPending`, so the module stays off; your Allow turns it on. A denied card leaves it off. The agent is built from the config cut down to what you allowed, and anything outside it asks with a normal card.
- **Grants live** (built 2026-11-06, after the restart): it listens to `PermissionChanged` for its subject ([`watch_grant`](../../../../../docs/api/infra.md#agent_access)) and calls `set_access(granted_config(...))`, so a widened grant reaches it with no off and on (an idle open session restarts once; a busy one at its next session). The agent may ask for more itself with `permissions.request`, and reads your snips with no card.
- **One [`ProfileAgent`](../../../../../docs/api/infra.md#profileagent)** with the job prompt: one job per session; `HANDOFF:` instead of the project's `handoff.ps1`; never submit or send (the user submits); confirm before any search. Its `claude` process starts on its first task, a fresh one per task, in Manual.
- **Chrome:** `chrome = true` starts its session with `--chrome` (the Claude in Chrome tools).
- **Searches:** each `job.search` is a background task, cancelled on stop. A reload waits while the agent has a task or a search runs.
- **The job UI** (built 2026-11-10, `ui.py`: `JobUi`): the job project's `Recruiters/scripts/job_ui.py`, what `job_ui.cmd` runs, a local server at `127.0.0.1:8781` with the Tracker, Job stack, Live search and Keywords pages. `job.open_ui` launches it the way `cv.open_tool` launches the CV Tool, through [`CompanionHandover`](../../../../../docs/api/app_kit.md#companionapp), but by its command line (`job_ui.cmd`'s: JobRadar's Python, `-I`, the script, plus `--port` and `--no-browser`), because it's another project's script with no JSON ping and no quit call: its ping is any 200 from `/tracker`, and the module's stop ends the server only if this module launched it (one you started yourself stays). The module opens the window itself, an Edge app window on its own profile (`window_profile("job_ui")`), whether it launched the server now or found it running. Each call first closes the window on that profile ([`close_app_windows`](../../../../../docs/api/app_kit.md#window): that window and nothing else; none open, nothing to close), then opens a fresh one ([`open_app_window`](../../../../../docs/api/app_kit.md#window)), so there's only ever one job UI window (the user's decision, 2026-11-10). It's always its own window, never a tab: without Edge, `job.open_ui` answers `not_available` instead of `open_app_window`'s browser-tab fallback, and the server always runs with `--no-browser`, so it opens no tab or window of its own. A job UI you start by hand with `job_ui.cmd` opens its own Chrome window, which isn't on that profile, so `job.open_ui` can't close it. A reload hands the running server to the new copy. Items that read or update the Tracker may follow.
- **"Open the UI" means `job.open_ui`** (the user's wish, 2026-11-10): one line, `UI_SHORTCUT` in `module.py`, is in the job agent's prompt and in its default description. The tab's Talker reads that description in its prompt ("{agent}'s job: …"), and so does `hub.agents`. So "open the UI" or "open the job UI" means calling `job.open_ui` straight away, with no searching for a tool and no looking in the folder. The Talker calls it itself when it has the door; without the door it hands the request to the agent.
