Core, Agent Hub and modules: a definition to approve

Groundwork for the second full restructure. A proposal, not approved, nothing built, no code changed. 2026-11-13. Every finding is in docs/next-steps/core-and-hub-definition.md with its file and line; the detailed call flows are on the piping page.

Your ask: tools, events and contracts harden how data gets in and out, so every call and every card passes the core's checks (router, permissions, the caller's mode), and the Agent Hub is a module that does agent coordination only. Each decision card is tagged with the part it serves: calls, cards, Hub.

In plain words: the Agent Hub grew up as the app's control centre, and it still holds three things that are not agent coordination: the module door every agent uses, the agent names, and the permission mode. They decide who is calling and whether a card shows, so they belong in the core.

The proposal: the core is what the app can't start without, plus seven ports (one new: Callers). Core modules are the assistant itself and depend only on the core. Add-ons are everything the assistant runs without. Three rules keep the line, each checked by a test. The Hub keeps tasks, focus, held questions, delivery and milestones.

A second pass (2026-11-13) read the code for eleven claims, one at a time. Each result, with its file and line, is in the note (V1 to V11). All of it was read from the code; nothing was tested by running it.

Verified:

  • V1 The three control events: ShutdownRequested is heard only by the core, which stops the app with no check (core/app.py:150-153); ResetRequested by every agent module (through AgentKit) and the Talker; AgentNotice only by the Hub. Any module may publish all three.
  • V2 The permission mode: the command SetPermissionMode (Hub, no sender check; sent only by temp_ui), the menu item hub.mode (Talker, Manual only).
  • V3 The lifecycle, read in full: cycle check at launch (registry.py:65-81) and at runtime (lifecycle.py:274-305); start in dependency order, stop in reverse; reload with roll-back. No permission check anywhere in it.
  • V4 A module added with modules.add isn't recorded: at the next launch it's off (found by folder) or gone (from elsewhere).
  • V5 The bus: one bounded queue per subscriber (100 by default), a full queue drops the event for that subscriber only; on turn-off, reload or remove the queued events are dropped and a running handler is cancelled.
  • V6 The door's token is an HMAC of the caller's name with a launch secret (infra/mcp_door.py:112-130, 173-175): a session can't claim another name.
  • V7 Task agents in Manual are asked before use_item; in Auto they aren't.
  • V8 The voice modules' files; voice_in asks for microphone before each session.
  • V9 The Main Assistant holds nothing that belongs elsewhere.
  • V10 Commands carry no sender, sends isn't enforced, and the answer handlers check only that the card or task id is open.
  • V11 A tool call from a module's own code passes no permission, mode or card check (core/tools.py:33-59).

Found different from the earlier text (corrected below):

4 · The definition

Core

What the app can't start without, plus the ports: the host (App), registry and loader, lifecycle, router, bus, container, config and logs, the directory with the core's menu, generated files, the permissions handler, and, new, the door and Callers. Shared code: contracts, infra, app_kit.

4Toolsmenus, InvokeTool, the doorcaller proved by the core's door (new); one gate: item callers, then risky items ask unless Auto (new)

Core modules

In the repo, on at launch, part of the assistant itself, depending only on the core: agent_hub (coordination only), talker, main_assistant, task_agents, temp_ui, console_io, usage, assistant_view, voice_in. Checked: each has group = "core" in its docs/docs.toml.

Add-ons

Everything the assistant runs without: html_viewer, voice_notes, cv, job_search, echo_orchestrator. Checked: group = "add-on".

5 · Decisions

The same seven cards as on the piping page. Tick one per card.

D1 · Where the door lives (calls · Hub)

  • (a) The core hosts it, as part of the Tools port
  • (b) It stays in the Hub, but the core stamps the caller itself
  • (c) Leave as is

Recommended: (a). The identity check belongs to the house, not to a tenant; today a module that provides IModuleDoor may name any caller.

Added by the check (V6, V11): whichever is chosen, mcp_config(caller) must check the name against the module asking (a config only for itself or the agents it claimed), and the menus must not be reachable as a plain IToolProvider contract with a free caller (G11, G16).

6 · Restructure sketch: not started

A rough order for you to look over. Nothing is approved or started. Every step from R2 on changes the core or the contracts, so each needs an app restart, asked first.

  • ☐ R1 · Boundary tests first. What: the rule 1 import test, rule 2 extended to config and module.toml, the rule 3 needs test. Why: they fence every later step. How: import and TOML reads in one boundaries test file. Done when: they pass on today's code and fail on a planted bad import.
  • ☐ R2 · Sender stamped, sends and publishes strict. Why: any module can send any command today. How: the sender filled by ScopedContext.send; one log-only run, then strict. Done when: an undeclared send is refused in a test; the full suite is green.
  • ☐ R3 · Callers port. What: agent names, kinds, modes and "you" move into the core; SetPermissionMode handled there. Why: the core's Auto check stops depending on the Hub. How: a callers part in the core provides IAgentNames; the Hub keeps only its open-card update as a listener. Done when: the handler sends no ListAgents; a module sending Auto is refused in a test.
  • ☐ R4 · The door in the core. What: DoorServer hosted by the app; IModuleDoor provided by the core; the "door host may name any caller" exception removed. Why: identity is checked by the core. How: move the hosting code out of agent_hub/module.py. Done when: agents reach modules with the Hub off; a module can't name another caller.
  • ☐ R5 · One gate on tool calls. What: risky menu items; dispatch_tool asks through Permissions unless Auto. Why: calls from code are never asked today. Done when: a module calling a risky item from code gets a card in Manual.
  • ☐ R6 · Events never control. What: the three control events become commands. Why: they're unchecked controls. How: every subscriber is traced (V1); the core's handler, which publishes AgentNotice, changes too. Done when: no event subscriber changes another part's state on request.
  • ☐ R7 · The review as a listener. Why: the core shouldn't start agent tasks. Done when: the handler sends no StartTask.
  • ☐ R8 · Docs and the overview diagram. Done when: the architecture overview shows seven ports and a Hub with coordination only.
