# Principles

The rules every design and implementation decision follows. If a change conflicts with one, raise it before proceeding. The decisions they led to, each with its reason, are in [decisions](decisions.md). Back to the [overview](README.md).

**The core controls communication; modules control functionality.**

1. **Modularity and ease of experimentation come first**, ahead of architectural sophistication for its own sake.
2. **Stable contracts, disposable implementations.** Modules depend on interfaces, never on concrete implementations.
3. **Loose coupling.** Modules never import each other's internals. Use menu tools for calls, contract interfaces for direct interactions, commands for explicit actions, and events for notifications. DI only ever resolves shared contract interfaces, never a module's concrete type.
4. **Minimal core.** No experimental or module-specific logic in the host. The core is what the app can't start without, plus its ports. Arrows point one way: an add-on may need the core or another add-on, and the core never imports, names or needs an add-on (`tests/test_boundaries.py`).
5. **Replaceable AI orchestration.** The model, agent framework, and orchestration logic are a module like any other.
6. **Module-owned state.** Each module manages its own state and exposes only what its contracts require.
7. **Independent lifecycles.** Modules can be initialized, started, suspended, and stopped independently.
8. **Graceful removal.** Removing an optional module must not break unrelated modules or require widespread changes.
9. **Technology independence.** Modules may later run out of process in other languages, so messages crossing module boundaries are plain, serializable data.
10. **Avoid premature complexity.** No distributed infrastructure, elaborate plugin systems, or speculative abstractions without an actual requirement. The one plugin mechanism is the module shape itself: modules found by folder, listed in the directory, and used through their menus ([modules](modules.md)).
11. **Runtime module control.** Every eligible module can be activated and deactivated independently through a central control interface while the app runs. The core owns lifecycle transitions; each module owns its resources and loads expensive ones only when needed. A module's `needs` start first, and turning a module off by hand is never refused (the modules that need it stay on). A module's code is hot-swapped in place, and if the new code fails the old code runs again. A module's code changes, and adding a new module, never need a restart; only changes to the core, contracts or shared helpers do, including a new contract or port type. Runtime configuration changes never need a rebuild.
12. **Interfaces by inheritance, functionality by composition.** Classes inherit only interfaces (`ModuleProtocol`, `Contract` subclasses) to establish contracts, and are assembled from composed parts to get behavior. No deep inheritance hierarchies: no intermediate base classes that carry implementation. Shared behavior is a shared part, not a shared parent. A module can provide a contract through a composed object: `ctx.provide(ITaskAgent, self._agent)`.
    - **Naming:** `I` prefix if and only if the class subclasses `Contract` (`IToolProvider`, `ITaskAgent`). `ModuleContext`, `Contract`, and concrete classes get no prefix. A **protocol** gets none either: it's an interface a class satisfies by having the right methods. A contract is different: a capability one module offers and others look up through the container. Example: `ModuleProtocol`, which every module satisfies.
    - **Mechanism:** contracts are `ABC`s, not `Protocol`s, because the core checks providers with `isinstance`.
    - **What contracts hold:** interfaces and plain data; a contract's code is limited to trivial defaults. One exception: `Menu` stays in `contracts`, because it is the menu contract itself, the one shape every module and the core share (principle 14).
13. **Build it once.** When two parts need the same behavior, it becomes one **reusable part**: written once, tested on its own, listed in the [reusable parts index](../api/reusable.md) with a **Used by** line, and used by both. A second copy is a bug.
    - **When it counts:** a second user exists or is in an approved change note, or the part implements a decided pattern (task agents, companion apps). "Might be useful one day" doesn't count (principle 10).
    - **What qualifies:** the behavior is the same, not just similar, and it knows nothing about any one module; a module's specifics come in as parameters.
    - **How:** by composition (principle 12): an object or function you compose, never a base class with code in it. Check the index before writing a helper. Where reusable parts live: [Reusable parts](reusable-parts.md).
14. **A module is a wrapper with a menu.** Every module is the same wrapper the core manages (a manifest with a one-line description, a lifecycle, a context) holding a menu of named tools, each with a description and its inputs: MCP-like, but ours only ([modules](modules.md)). Refines 3 and 12.
    - **Today:** the wrapper, the one-line description and the `Menu` part are built, and most modules have menu items (the viewer, the Hub, the Talker, `task_agents`, `job_search`, `cv`, `usage` and the core's own).
15. **Directory, then menu.** The Talker and the Main Assistant find capabilities the same way, one line per module first, then only that module's menu, then `InvokeTool`; no agent has another module's tools written into it ([modules](modules.md)). **One road:** what one module does for an agent on another module goes through that module's menu, not a side command, so the item's caller check applies (e.g. the Talker's mode switch and card answers are `hub.mode` and `hub.answer`, for the Talker only).
    - **Today:** both agents find and call modules through the one MCP door, which the core hosts. A SHOW tag is parsed in one place (`show_page`), and the page opens through the page-opener contract (`open_page`, `IPageOpener`), never through a viewer's own name ([`show_page`](../api/infra.md)).
16. **Chain, don't glue.** A module uses another only through what that one declares (its events, commands, or menu), and a shared service serves several users through sessions with a destination each, never through copies of itself ([modules](modules.md)). Refines 3; it's 13's "build it once" for running services.
    - **Today:** events between modules and the voice contract's sessions are built; the voice service takes one listener at a time, so one session runs at once.
17. **Declared dependencies, found by folder.** A module is its folder: the core finds it there (in the repo's modules folder and the extra `[core] module_folders`) and first starts whatever provides the contracts its manifest `requires`; a module depends on contracts, and lists by id (`needs`) only the modules it can't run without. A module may turn on the add-on it chains to at the moment it needs it (`ActivateModule`; the core still asks that module's access card, and the reply comes back as its named events) ([modules](modules.md)). A contract it only looks up at each call, with no start order, goes in `uses` (e.g. the agents' door, names and page opener, `AGENT_USES`). A subscription or lookup the manifest doesn't declare is logged once. Extends 11.
    - **Today:** built; voice notes requires the voice contract, not `voice_in`.
18. **One job per class; a small orchestrator with handlers.** A module's main class (and any big class) wires parts together and decides; each separate job (a state machine, a server, a card flow, a protocol) is its own class in its own file, composed in. A file over about 400 lines or a function over about 40 is a signal to split, not a rule (e.g. the Agent Hub: `AgentHubModule` wires a `TaskBoard`, a `Focus` and a `Reviewer`, each in its own file). Extends 12.
19. **Name a concept once.** A concept used in two places (a kind of question, a display name, an id scheme, a default, a limit) is one type, enum or constant with one owner, imported by the rest. Facts cross boundaries as typed fields, never as text prefixes another part has to parse (e.g. `QuestionKind` on a task's updates: the Hub reads the agent's `Risky:` once, everyone else checks the kind; `MAX_SNIPS` in the contracts). Refines 9 and 13.
20. **Dispatch by table.** Where code picks one of several handlers (tags, routes, card actions, engines, tools), it looks the handler up in a table it registers into, so adding a case is adding an entry, not editing a chain.
21. **Shared code names no module.** The core, the contracts and the shared helpers never name a module, its id or its tools; those come in as config or parameters (e.g. the permissions reviewer, "you" and the relays, in `[core.permissions]`). A module names only what it declares in its manifest, and its manifest declares everything it uses. Refines 4, 15 and 17.
    - **Today:** two exceptions are open: `core/callers.py` reserves the ids `hub` and `talker`, and `core/permissions/handler.py` maps a `talker:` prefix to its pair's mode ([decisions](decisions.md#open-decisions)).
22. **Inject what you'd swap.** A part that talks to a process, a network or another part takes it as a constructor argument instead of building it inside, so tests and replacements plug in without patching. Not a reason for new interfaces (principle 10): pass the concrete object.

The code doesn't follow principles 18 to 22 everywhere yet (the [code map](code-map.md) shows how the parts fit today).
