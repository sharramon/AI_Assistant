In plain words: keep the add-ons in the repo for now, but make the line between the core and the add-ons hard, with three rules that tests check.

Cut the CLAUDE.md cost two ways. The repo's CLAUDE.md loads only a short overview, and each module's API stays on its own docs page. Module agents skip the repo's CLAUDE.md (claudeMdExcludes), load a short developer-rules file in its place (they write code, so they need the rules, not the bulk), and work in a data folder outside the repo, where your CVs, job state and outputs live.

Later, when the core's contracts stop changing, move the add-ons to their own folder outside the repo, each with its own CLAUDE.md. Each add-on is already one folder, which makes that move cheap.

0 · A tool call, a command and an event between two modules, as the code is built

teal T1 to T4: a tool call grey C1 to C3: a command blue E1, E2: an event dashed with a hollow head: the answer coming back red ✗: never
  • T A tool call. job_search's code runs ctx.send(InvokeTool(name="cv.task", args=…)) (T1). An agent does the same through the door D1, which proves the caller by its token and hands the call to the router as the core's own. The router D3 checks that InvokeTool is in job_search's sends, stamps job_search as the caller, and passes it to the one handler for InvokeTool: the gate D4 (T2). The gate finds the one module offering cv.task, starts cv first if it's off and start_on_use, checks the arguments and the item's callers, asks you on a card if the item is risky, and calls cv's item (T3). The Result goes back the same way (T4).
  • C A command. job_search runs ctx.send(DeliverMessage(…)) (C1). The router checks sends, stamps sent_by, and refuses a control command unless it comes from you. It then passes the command to the one handler registered for its type (C2): the Agent Hub's. The Hub registered that handler at its start with ctx.handle(DeliverMessage, …) and listed it in its manifest's handles. The Result goes back to the sender (C3).
  • E An event: how a listener subscribes and how it's triggered. Subscribe: in its start(), voice_notes calls ctx.subscribe(VoiceTranscript, on_text) and lists VoiceTranscript in its manifest's listens. For a named event, a module calls ctx.subscribe_named("cv.job_finished", on_cv) (or "cv.*") and lists it in listens_named, as job_search does. Trigger: voice_in calls ctx.publish(VoiceTranscript(…)) (E1). For a named event, cv calls ctx.publish_named("cv.job_finished", data), which must start with cv's own id and carry plain JSON. The bus returns at once and calls every subscriber's handler with its own copy, each on its own worker and queue (E2). A full queue drops the event for that listener and logs it. The publisher gets nothing back; if it needs a reply, the replying module publishes its own event with the same correlation id.
  • ✓ Nothing else connects modules. When a module stops, the core removes its subscriptions, handlers and menu (ctx.close). Modules never import each other's code. The fourth way is a contract: a service one module provides into the core's container and another uses, such as the voice contract IVoice.
  • ≠ Where the code differs from the piping page: (a) the door doesn't call the gate directly. It sends InvokeTool through the router (core/door.py, core/app.py:110,134), so agents and module code share one path: router, then gate. The b pictures below draw door → gate, as on the piping page. (b) Listening isn't strict. A subscription the manifest doesn't list still works and is only logged once (core/context.py:224-231). The same goes for a named event the manifest doesn't list, if its name starts with the module's id. Only sends, the typed publishes, handles and provides are strict.

What the loader can do today, and what would need to change

  • L Loader (core/loader.py): it has no setting for an extra module folder. It finds modules as sub-packages of assistant.modules, and find_modules and app_folders already loop over every folder in that package's __path__. Adding the outside folder to assistant.modules.__path__ at startup, from one config line, would let it find them, with their import names (assistant.modules.<id>) and reloads unchanged. That's a small change, but it's in the core, so it needs a restart.
  • A Agent folders (infra/agent_access.py): MODULES_FOLDER is fixed to the repo's modules/. An outside add-on would get no own-folder write grant and no relative workspace path until it asks the loader instead.
  • D Docs build (scripts/build_docs.py): MODULES_DIR is the repo folder, so an outside add-on's docs pages and module-library row would be missing.
  • T Tests and lint: pyproject.toml's testpaths and ruff's src name the repo folder. test_find_modules, test_module_docs and the tripwires in test_module_folders read the repo folder or run git grep and git check-ignore in this repo only.
  • C Architecture checks and contracts: the boundary checks would have to scan two folders. A contract change would touch two folders and two git histories, with no single commit and an add-on's tests needing the matching core. The overnight migration changed every module in one pass, which is easy only in one repo.
  • P Prompt and grant: the Main Assistant's prompt names src/assistant/modules/ for reloads. Saved grants exist today, but a grant that ends with the session needs checking, and may be new.

Appendix B · The rules for the core line

  • 1 The core is what the app can't start without, plus the ports.
  • 2 Modules talk only through tools, events and contracts, and never import each other's code.
  • 3 Arrows point one way: an add-on needs the core or another add-on, and the core never names an add-on.

Already checked by tests: the core group names no add-on, and every add-on has its tripwire (checklist items 15 and 19). Built 2026-11-13 (restructuring R1): tests/test_boundaries.py checks all three rules: modules import only contracts, infra, app_kit, the standard library, third-party packages and their own package; core config and core modules name no add-on; a core module's needs name only core modules.
