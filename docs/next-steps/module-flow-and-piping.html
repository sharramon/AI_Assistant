Module flow and piping: a quick guide

How the assistant's parts fit together and how a call travels between them, in six pictures from simple to detailed. Read top to bottom; each picture has only the notes needed to read it.

Who is who

  • You talk with the Talker. The Main Assistant does the work and coordinates helpers: task agents, and module agents such as cv_agent and job_search_agent. Each agent is its own Claude Code session.
  • The core is what the app can't start without: the host, its six parts (D1 to D6: the module door, Callers, the router, the one gate, the bus, the permissions handler and its cards) and the core modules (talker, main_assistant, agent_hub, task_agents, temp_ui, usage, console_io, assistant_view, voice_in).
  • The Agent Hub is a core module that only coordinates: the task board, the focus, held questions and message delivery. temp_ui is the app's window, where cards show with buttons.
  • Add-ons are every other module (cv, job_search, html_viewer, voice_notes, echo_orchestrator), each one folder, src/assistant/modules/<id>/.
  • Agents reach every module through the core's door, with three tools: list the modules, show a module's menu, use an item on it.

1 · Core and add-ons: the three rules

The core is what the app can't start without; every other module is an add-on. Three rules keep the line between them hard, and tests/test_boundaries.py and tests/test_module_folders.py check them.

  • 1 The core is what the app can't start without, plus the ports.
  • 2 Modules talk only through tools, events and contracts, and never import each other's code.
  • 3 Arrows point one way: an add-on needs the core or another add-on, and the core never names an add-on.

2 · How modules talk through the core

The three ways one module reaches another: a tool call, a command and an event. Each passes through the core.

teal T1 to T4: a tool call grey C1 to C3: a command blue E1, E2: an event dashed with a hollow head: the answer coming back red ✗: never
  • T A tool call: "do this and tell me the result". job_search's code runs ctx.send(InvokeTool(name="cv.task", args=…)) (T1). An agent does the same through the door D1, which proves the caller by its token and hands the call to the router. The router D3 checks that InvokeTool is in job_search's sends, stamps job_search as the caller, and passes it to the one handler for InvokeTool: the gate D4 (T2). The gate finds the one module offering cv.task, starts cv first if it's off and start_on_use, checks the arguments and the item's callers, asks you on a card if the item is risky, and calls cv's item (T3). The Result goes back the same way (T4).
  • C A command: one message to the one module that handles it. job_search runs ctx.send(DeliverMessage(…)) (C1). The router checks sends, stamps sent_by, and refuses a control command unless it comes from you. It then passes the command to the one handler registered for its type (C2): the Agent Hub's, which it registered at its start with ctx.handle(DeliverMessage, …) and lists in its manifest's handles. The Result goes back to the sender (C3).
  • E An event: "this happened", to whoever listens. To listen, voice_notes calls ctx.subscribe(VoiceTranscript, on_text) in its start() and lists VoiceTranscript in its manifest's listens. For a named event, a module calls ctx.subscribe_named("cv.job_finished", on_cv) (or "cv.*") and lists it in listens_named, as job_search does. To publish, voice_in calls ctx.publish(VoiceTranscript(…)) (E1); cv calls ctx.publish_named("cv.job_finished", data), whose name must start with cv's own id and whose data is plain JSON. The bus returns at once and gives every listener its own copy, each on its own worker and queue (E2). A full queue drops the event for that listener and logs it. The publisher gets nothing back; if it needs a reply, the replying module publishes its own event with the same correlation id.
  • Good to know: (a) the door sends InvokeTool through the router, not straight to the gate (core/door.py, core/app.py:110,134), so agents and module code share one path: router, then gate. Pictures 3 and 6 draw it short, as door → gate. (b) Listening is loose. A subscription the manifest doesn't list still works and is logged once (core/context.py:224-231); so does an unlisted named event whose name starts with the module's id. Only sends, the typed publishes, handles and provides are strict.

5 · The agents: where each works and which CLAUDE.md it loads

Each agent is its own Claude Code session. The Talker and the Main Assistant work in the repo and load a small CLAUDE.md; the module agents work in their own workspace and skip it.

  • 1 The repo's CLAUDE.md is small: it imports only the short overview. The API index covers the core only, and each module's API is on its own docs page in its folder. So the Talker's and the Main Assistant's base context stays the same size however many modules there are.
  • 2 The Main Assistant hands work on: hub.start and hub.send go through the door and gate to the Hub's menu. A helper reports back with a STATUS line, which the Hub turns into a report for the Main Assistant's next turn.
  • 3 Module agents skip the repo's CLAUDE.md: claudeMdExcludes is passed per agent with --settings (one more argument in claude_command, set from AgentProfile). They write code, so a short developer-rules file loads in its place, without the overview and the API index.
  • 4 Each module agent works in its workspace: the module's own modules/<id>/workspace (gitignored), or your data folder outside the repo if config/<id>.toml names one. It edits its own code through a write grant on its module folder, on the same access card (P7 in picture 3).

6 · Add-ons kept in a folder outside the repo

By default every add-on is in the repo. The [core] module_folders setting lets the loader find add-ons in another folder too (C:/AddOns here is an example), and they are reached through the same core. The red marks are the known gaps.

  • A1 Found the same way: at launch the loader adds each module_folders folder to assistant.modules.__path__, and loader.find_modules takes every sub-folder, with the same id check (core/loader.py:143-166). The LifecycleManager keeps every class, on or off, and starts one with init, link_menu and start (A9).
  • ✓ Reached the same way: an add-on in C:/AddOns gets its tool calls through the same door and gate (1, 2) and its cards through the same handler (7 to 13). It uses the same Callers, router and bus, and its agent's folder grants go on the core's own card. There is no separate path. The numbered arrows and the ≠ marks are as in picture 3.

Known gaps

  • !1 "You" is trusted by module id (core/callers.py:80, config/default.toml:45-46), not by the folder the code came from. A module in C:/AddOns named like a core module (temp_ui, say) would get your rights. Only tests/test_boundaries.py:180 catches it, and only when pytest runs.
  • !2 job_search reads cv's output by file path, not through a tool: the job project's cv_output link in job_paths.json points into cv's workspace. That goes past the door, so wherever cv's workspace sits, the link has to point there.
  • !3 The "found in two folders" check runs only at startup (core/loader.py:156). A module added later with modules.add isn't checked (core/lifecycle.py:172-188).
  • !4 The modules.add card doesn't show which folder the code comes from (core/tools.py:107-109).
  • !5 The CLAUDE.md exclude list covers only the repo's files (infra/agent_profile.py:121-125). An agent working under C:/AddOns/<id>/ would load any CLAUDE.md it finds in a parent folder there, and the developer rules point at repo paths it can't read.
  • ! The microphone isn't asked: voice_in asks ctx.permissions.request("microphone") before each session, but a single-name request only logs and allows (core/permissions/port.py:29-35), so you're never asked (A12 in picture 4).
  • ? Your open decision (G17): do the Talker's card answers count as yours? The Talker may send them (≠4 in picture 3); whether it should is yours to decide.
