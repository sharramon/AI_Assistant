job_search: architecture

Interface
Tools job.search(days): answers at once; the result reaches the caller as an AgentNotice at its next turn (a command the Hub handles; the line reads [job_search] …, labelled with the sending module). A stub today: the notice says the runner isn't built. job.open_ui(): opens the job UI in its own window on the Tracker, every time: starts the server first if it isn't answering, closes the job UI window already open, then opens a fresh one, so there's only ever one; gives {url, launched, window}, or not_available if it can't start. job.tailor_cv(company, role, base_cv, jd_text or jd_file, …), only for the job agent (anyone else: not_available): answers at once; in the background it turns cv on (ActivateModule; if cv_agent's card is open it waits for ModuleStateChanged active, or a Deny in PermissionChanged, up to cv_wait), sends cv.task with for_agent = its agent, and tells the agent with one DeliverMessage: the job was taken (cv_taken_text), or cv couldn't come on, ask the user whether to use the base PDF untailored (cv_untailored_text) (on-demand chaining, 2026-11-13)
Handles nothing: the agent is called through ITaskAgent, the menu through InvokeTool
Calls ctx.permissions.request_set on start (through request_access); ReportTask; DeliverMessage to its own agent (cv's events, job.tailor_cv's outcome); ActivateModule("cv") and InvokeTool cv.task (job.tailor_cv); listens to ModuleStateChanged and PermissionChanged while it waits for cv; AgentNotice (job.search's result, a command the Hub handles); the Hub's menu through the core's door, as job_search_agent; IAgentNames, the core's Callers (ProfileAgent claims the id on start, releases it on stop)
Publishes AgentActivity, AgentStateChanged, SessionUsage, PermissionModeChanged
Listens to ModuleStateChanged, PermissionChanged (above). The job agent's reset is the ResetRequested command, which the Hub handles by calling its ITaskAgent.reset. cv's named events (ModuleEvent) cv.job_finished and cv.job_submitted: one whose reply_to is its agent becomes one DeliverMessage waking it (cv_finished_text: the job, the folder, cv's one-line summary, "update this job's row in the tracker", cv.read_result task_id=…; cv_submitted_text: cv's summary, the folder, the tracker row, carry on). The agent updates the tracker; the module writes nothing into the job project. An event published while job_search is off or reloading, or across an app restart, is lost (the bus keeps nothing); that's accepted, with no fallback (decisions, 2026-11-13)

Owns and launches

  • Its access, asked for on start: start asks for the whole list in one request (request_access, subject job_search_agent). If the saved grant matches the list, the agent is built at once. Otherwise a card opens and the start ends with AccessPending, so the module stays off; your Allow turns it on. A denied card leaves it off. The agent is built from the config cut down to what you allowed, and anything outside it asks with a normal card.
  • Grants live (built 2026-11-06, after the restart): it listens to PermissionChanged for its subject (watch_grant) and calls set_access(granted_config(...)), so a widened grant reaches it with no off and on (an idle open session restarts once; a busy one at its next session). The agent may ask for more itself with permissions.request, and reads your snips with no card.
  • One ProfileAgent with the job prompt: one job per session; HANDOFF: instead of the project's handoff.ps1; never submit or send (the user submits); confirm before any search. Its claude process starts on its first task, a fresh one per task, in Manual.
  • Chrome: chrome = true starts its session with --chrome (the Claude in Chrome tools).
  • Searches: each job.search is a background task, cancelled on stop. A reload waits while the agent has a task or a search runs.
  • The job UI (built 2026-11-10, ui.py: JobUi): the job project's Recruiters/scripts/job_ui.py in the module's workspace (what the old project's job_ui.cmd ran), a local server at 127.0.0.1:8781 with the Tracker, Job stack, Live search and Keywords pages. job.open_ui launches it the way cv.open_tool launches the CV Tool, through CompanionHandover, but by its command line (job_ui.cmd's: JobRadar's Python, -I, the script, plus --port and --no-browser), because it's another project's script with no JSON ping and no quit call: its ping is any 200 from /tracker, and the module's stop ends the server only if this module launched it (one you started yourself stays). The module opens the window itself, an Edge app window on its own profile (window_profile("job_ui")), whether it launched the server now or found it running. Each call first closes the window on that profile (close_app_windows: that window and nothing else; none open, nothing to close), then opens a fresh one (open_app_window), so there's only ever one job UI window (the user's decision, 2026-11-10). It's always its own window, never a tab: without Edge, job.open_ui answers not_available instead of open_app_window's browser-tab fallback, and the server always runs with --no-browser, so it opens no tab or window of its own. A job UI started by hand with the old project's job_ui.cmd opens its own Chrome window, which isn't on that profile, so job.open_ui can't close it. A reload hands the running server to the new copy. Items that read or update the Tracker may follow.
  • "Open the UI" means job.open_ui (the user's wish, 2026-11-10): one line, UI_SHORTCUT in module.py, is in the job agent's prompt and in its default description. The tab's Talker reads that description in its prompt ("{agent}'s job: …"), and so does hub.agents. So "open the UI" or "open the job UI" means calling job.open_ui straight away, with no searching for a tool and no looking in the folder. The Talker calls it itself when it has the door; without the door it hands the request to the agent.
