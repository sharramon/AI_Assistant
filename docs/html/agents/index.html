Agents

How we run and work with the agents: setup, experiments, and what we've learned. How they fit the system is on the Agents architecture page.

Status: built (2026-10-25): Talker, Main Assistant, and Agent Hub, launched by python -m assistant, shown in the temp UI. See Agent runtime. Next: self-improvement.

Roles

Agent Job First implementation
Talker Talks with you; hands off work; reports progress; relays questions claude -p session, faster model (sonnet), no built-in tools
Main Assistant Your main AI: reasons, plans, does the work, delegates claude -p session (Claude Code) with file tools
Subagents Specialized workers the Main Assistant delegates to Claude Code's own subagents, inside the Main Assistant's process: debugger (.claude/agents/debugger.md, sonnet) for debugging loops and broad searches. Hub subagents (separate tasks you can stop one by one) later, if needed

How the sessions run

  • Each agent is one claude -p --input-format stream-json --output-format stream-json process. The Talker's is long-lived, so it keeps the conversation. The Main Assistant gets a fresh one per task, and per handoff within a task, so a task's context holds only that task (fresh sessions and handoffs).
  • Usage: each session's context now (what every call resends) and its tokens and ~$ since launch, worker and Talker apart. The Talker always knows both and warns you past 150k; the temp UI shows both live. A Reset starts either one fresh.
  • Messages in and out are JSON lines over stdin and stdout. The owning module, through ClaudeSession, writes the agent's input and reads its event stream.
  • Transcripts for debugging: every line in and out goes to talker.jsonl and main_assistant.jsonl (transcript in each module's config, a file name), next to the app's own assistant.log, in one folder per launch: logs/<start time>_<theme>/ (Logging).
  • Agents never talk to each other directly; everything goes through the Hub and the core.
  • Started with --strict-mcp-config, so your claude.ai MCP connectors aren't loaded.
  • Runs on your Claude subscription (terms checked for personal use). The session layer stays swappable to an API key.

Permissions

  • Talker: no tools.
  • Main Assistant: for now, the same access as Claude Code in this repo (decided 2026-10-26). Every built-in tool (tools = "default", shell included), acceptEdits mode, and the repo as its working folder, so it loads CLAUDE.md and reads the docs like Claude Code does. Settings in [modules.main_assistant] (workspace, read_dirs, write_dirs, allowed_commands):
Access Where
Read and write, without asking the whole repo, including its own source, plus .claude/skills and .claude/agents (listed in write_dirs because claude treats .claude/ as sensitive)
Run, without asking allowed_commands: the tests (.\.venv\Scripts\python -m pytest), .\.venv\Scripts\ruff check, the docs build, read-only git (git status, git diff, git log, git show), and Get-ChildItem, Get-Content, Select-String, with any arguments (added 2026-11-02)
Asks you, each time other shell commands (git commit, push, reset, checkout, deleting files, installs, network, scripts it writes itself), the rest of .claude/, anything outside the repo

Its debugger subagent works under the same rules; its requests come to you the same way (checked 2026-10-27).

Both agents' prompts state these permissions, so they don't have to find out by trying. The repo zones are recorded but not enforced until the permissions handler and branch workflow are built. - Permission requests: when it uses a tool its rules don't allow, the request comes to you: Allow / Deny buttons on a card in the temp UI's Talker pane, or tell the Talker yes or no. Each answer covers that one use. Unanswered requests are denied after 10 minutes (permission_timeout). The Talker never answers on its own. How it works: the note. - "You" means both. To you the Talker and the Main Assistant are one assistant, and both prompts say so.

First implementation limits

  • One Main Assistant and one active task; another request gets "busy". No queue.
  • No scheduling or distributed machinery until needed.

Workflow skills

Project skills in .claude/skills/, used by Claude Code and the Main Assistant alike. CLAUDE.md says when each applies.

Skill What it's for When
batching The batching rules that keep the step count and per-step cost down Before any multi-step task (several reads, edits, builds, or questions)
architecture-first Confirms the use-case, checks the architecture docs and API reference so code gets reused, keeps those docs updated Before non-trivial edits, or a change touching more than one function or file
architecture-check Checks what was just built for modularity, reuse, and fit with the main app; the final report gets an "Architecture check" section After each big chunk of a multi-chunk build, and before the final report
