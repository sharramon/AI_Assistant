Module control

Turning modules on and off while the app runs. The core handles these commands; any module may send them (a control panel, or an agent asked to "enable the browser module"). All items: from assistant.contracts import .... Back to the API index. How it works: runtime module control.

Every module listed in src/assistant/__main__.py is available; modules.enabled in config only sets which are active at startup.

ListModules

ListModules() (command)

The module directory: every available module, one line each (its id, one-line description and current state).

Returns: Result.ok(list[ModuleInfo]), in the order the modules are listed in __main__.py.

Example

result = await ctx.send(ListModules())
active = [m.id for m in result.value if m.state is ModuleState.ACTIVE]

The core's menu

Module control as menu items, under the id core (GetMenu(module_id="core")), called with InvokeTool like any module's items. Each sends the matching command above, so results and errors are the same.

Item Arguments Sends Asks first
modules.list none ListModules no
modules.menu module_id GetMenu no
modules.docs module_id (the core reads the module's own docs/ folder) no
modules.on module_id ActivateModule no
modules.off module_id, with_dependents (false) DeactivateModule with with_dependents
modules.reload module_id, now (false) ReloadModule no
modules.add package, activate (true) AddModule yes
modules.remove module_id, settings ("keep" or "purge", required) RemoveModule (purge when "purge") yes
permissions.grants none (the handler) no
permissions.grant module_id, items (keys), subject (the handler) from an agent: your card
permissions.request read, write, commands (lists), python, chrome, reason (the handler) always your card
permissions.revoke module_id, subject, items (keys; none: all) (the handler) from an agent: your card

modules.docs returns the module's own docs, on or off: a list of {"title", "path"}, one per page in its folder's docs/ (order and titles from module_docs), [] if it ships none, invalid_arguments for an unknown id. An agent learns what a module does from the module itself: its menu, then these pages. Added 2026-11-06.

"Asks first" for modules.* goes through the core's ctx.permissions (modules.off_with_dependents, modules.add, modules.remove, whose reason says keep or delete its settings); single names aren't checked yet, so they're allowed and logged. Refused → failed ("Not allowed: …"). Through InvokeTool a call is capped by its timeout (30 s by default); a reload or add that takes longer still finishes, and ModuleStateChanged reports it.

The permissions.* items are the permissions handler's grant calls (PermissionsMenu). permissions.grants lists the saved grants per module and subject (the kind of agent): what was granted, the date, and whether the current list still matches. permissions.grant widens a grant with asked-for items, and a module that's off is turned on; one that's on takes it live (from its agents' next session, at once when idle). permissions.request is an agent asking for more access for itself (its module and subject come from its id; folders resolved); on Allow the items join its grant as added items, and a running agent takes them live. permissions.revoke takes back all or some items; the module turns off right away and its running tasks are stopped. From you (a UI you click in, temp_ui by default) they apply at once; from an agent they show you a card, and the answer reaches the agent as a note.

ActivateModule

ActivateModule(module_id: str) (command)

Turn a module on: a fresh instance, then init and start.

Parameters

Name Type Required Description
module_id str yes The module's manifest id

Returns

Status When
ok It's active (or already was). Any sole provider of a contract it requires was activated first
invalid_arguments No module has that id
not_available It requires a contract that no available module provides
failed Several modules could provide a required contract (the error lists them; activate one first), it would be a second provider of a single-provider contract, a required provider failed, or its own init/start raised. In the last case its state is failed and it can be retried
timed_out The command timed out; the activation still finishes, and ModuleStateChanged reports the outcome

Example

result = await ctx.send(ActivateModule(module_id="voice_output"))
if not result.is_ok:
    ctx.log.warning("Couldn't enable voice output: %s", result.error)

Start on use, by contract: turn on the module that is off, declares contract (a contract's class name, e.g. "IPageOpener") in its manifest.provides, and has start_on_use = true in its config, the same way as ActivateModule. ReloadModule

ReloadModule(module_id: str, now: bool = False) (command)

Swap a module's code while the app runs: stop it, import its package fresh (with every submodule), re-read its config section, start the new code. Active modules that require something only it provides are stopped and started around it. If the module says it's busy, the reload waits until it isn't (up to core.reload_idle_timeout, 300 s), unless now, which cuts in. The old instance's export_state reaches the new one as ctx.handover. How it works: reloading.

Returns

Status When
ok The new code runs (or is loaded, if the module was inactive)
invalid_arguments No module has that id
failed Its code is shared (core, contracts, infra, app_kit) or not in its own package; it stayed busy past core.reload_idle_timeout (the error says why, and to use now); or the new code failed to import, init, or start. Then the old code is put back and started, and the error says so

Example

result = await ctx.send(ReloadModule(module_id="voice_in"))

AddModule

AddModule(package: str, activate: bool = True) (command)

Load a module that wasn't there at launch, from its package, and activate it unless activate is false. Its package must export exactly one ModuleProtocol subclass; under assistant.modules, its folder must be named with its id, else it fails. The next launch finds it by folder; add it to modules.enabled to start it then.

Returns

Status When
ok Value: the new module's id
failed Already loaded (use ReloadModule), an id that's taken, an import error, or its code needs a contract the running app doesn't have: new contracts and port types need a restart

RemoveModule

RemoveModule(module_id: str, purge: bool = False) (command) · built 2026-11-13 (module folders item 16)

Remove a module from this run: turn it off if it's on, and take it out of the module list, so ListModules and GetMenu don't offer it until AddModule loads it again. Sent by the core's modules.remove, which asks first. How it works: runtime module control.

  • Refused while needed: by an active module that needs it or requires something only it provides, or by one in modules.enabled (re-read from config/ when the app has a config loader) whose needs lists it, on or off.
  • purge: deletes config/<id>.toml and config/<id>.local.toml (in the app's config directory: App(config_dir=...), else ASSISTANT_CONFIG_DIR, else config/), and nothing else. An id that names a shared file (default, local, modules, permissions, voice_service) has none to purge. Without purge, nothing is deleted.
  • Never: deletes the module's folder, or rewrites config/modules.toml. If it's in enabled, the result tells you to take it out, or it starts again at the next launch.

Parameters

Name Type Required Description
module_id str yes The module's manifest id
purge bool no Delete its two settings files (modules.remove's settings="purge")

Returns

Status When
ok Value: {"module_id", "deleted": [paths], "kept": [paths], "folder": path or None, "enabled": bool, "message": str}; message says what was deleted or kept, whether to edit enabled, and that the folder is yours to delete
invalid_arguments No module has that id
failed Another module needs it (the error names them), or it couldn't be turned off. Nothing is deleted

Example

result = await ctx.send(RemoveModule(module_id="weather", purge=True))
