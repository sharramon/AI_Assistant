Decisions

What's decided (each with its reason), what's still open, and what's deliberately deferred. The detail of each lives on the page it links to. Back to the overview.

Decided

Platform

  • Core and PC-side modules: Python.
  • Quest 3 client: a separate Unity (C#) app, connecting through the gateway module (remote clients).
  • Deployment: a PC for now, a server later.
  • Agent runtime: claude -p sessions on the subscription. Why: the terms allow it, and each agent gets Claude Code's tools (agent runtime).
  • Views: a throwaway temp UI (a local web page in its own window: Main Assistant left, Talker right) plus terminal 1; terminal 2 (assistant_view) is off by default. Why: a stand-in until the UI handler is designed (see Open).
  • Independent apps where it pays off: a part that is useful without the assistant is its own app. It never imports assistant; a thin module launches it and talks to it both ways (its local HTTP API one way, its event stream the other). Its code lives in its module's app/<package>/ (html_viewer, cv_tool, voice_service). Why: it can run and be tested alone, while the modules inside the main app stay one process (HTML viewer, modules).

The core line

  • Core and add-ons: the core is what the app can't start without, plus its ports: the host, the core modules (each module's docs/docs.toml says group = "core"; voice_in is core), the module door with its gate, and the seven ports. Every other module is an add-on. Arrows point one way: an add-on may need the core or another add-on, and the core never imports, names or needs an add-on. tests/test_boundaries.py and tests/test_module_folders.py guard all of it (D7). Why: any add-on can be added, swapped or removed whole without touching the core (core, modules).
  • Modules talk only through tools, events and contracts (assistant.contracts), never by importing each other. Shared helpers are assistant.infra and app_kit. Why: a module's code can be reloaded or replaced without breaking the others (principles 3 and 16).
  • Router and bus (D3, D5): a command asks for something: it goes to one handler, gets a Result, and carries its sender, stamped by the core (Command.sent_by). An event only reports: it is published, and anyone may listen. Control is never an event, so ShutdownRequested, AgentNotice and ResetRequested are commands. A module may send and publish only what its manifest lists, and control commands come only from you. Why: a command has one handler and a checked sender, while an event can't be stopped or traced to who asked (communication).
  • Commands carry sent_by, not sender: DeliverMessage.sender already means the agent a message is from.
  • What isn't a control command: ActivateModule (the module's own access card guards its start, and a module may turn on the add-on it chains to), CancelTask (it goes through the Hub's menu, which checks the caller) and SetPermissionMode (the core's handler checks the mode itself). ShutdownRequested is gated by the strict sends check alone. Why: the core names no add-on, and each of these has its own check (communication).
  • Runtime module control: modules are turned on and off while the app runs, through the core's control commands and the core's menu (modules.*). A module's code is reloaded in place, and a new module added, without a restart. Only changes to the core, contracts or shared helpers need one, including a new contract or port type. Why: experimenting with modules is the point of the platform (core).

Modules

  • Module shape: every module is a wrapper (manifest, lifecycle, context) with a menu of tools. Agents find modules through a one-line directory and open only the menu they need. The core finds modules by folder. Dependencies are by contract (requires), with needs naming only the modules one can't run without. Why: one shape for every module keeps the core small and the agents' context short (modules, principles 14 to 17).
  • One MCP door with three tools (list modules, show a menu, use an item), hosted by the core (D1). mcp_config(caller) answers only for the asking module or the agents it claimed, and menus sit in a core-private table, not the container. Modules never speak MCP; an outside tool with its own MCP becomes a module that is an MCP client. Why: an MCP server per module would bypass the gate, the directory, the links between modules and hot swap (core, modules).
  • Module folders: everything of a module is in src/assistant/modules/<id>/: its code, module.toml (defaults, needs, packages), app/, tests/ and docs/. config/ holds only your choices (config/<id>.toml per module, gitignored, plus config/modules.toml and config/permissions.toml). generated/ is built by the core and safe to delete. Why: delete a module's folder and nothing of it is left except your choices (modules).
  • Add-on folders outside the repo ([core] module_folders): absolute paths only, empty by default. Each folder is added to the assistant.modules package path after the repo's own, so an outside module keeps its import name. An id found in two folders stops startup. Why: add-ons can live outside the repo with nothing else changed, and the copy that runs is always the one you meant (modules).
  • How general event types are: a module-owned event is one generic named ModuleEvent (name, source, data), published under the module's own id and matched by name. Shared events (the core's, the Hub's, ones several modules agree on) are typed classes in assistant.contracts. A named event that becomes widely used gets a typed class at the next planned restart. The bus keeps no queue for missed events. Why: the bus matches by class, so a typed event per module would mean a contracts change and a restart for each one, and a module can't own a class that survives its own reload (communication).
  • Modules report back through named events; tools are for calls out: an agent asks a module for work with a tool (cv.task), and the module answers by publishing a ModuleEvent (cv.job_finished) carrying the asker's id. The asker's module subscribes and wakes its own agent (DeliverMessage). There is one path only (StartTask.tell_parent=False) and no fallback for lost events: an event published while the listener is off is lost. Why: at-most-once delivery is enough, since with the listener off nobody would act on it, and the result stays in the Hub's task record and the job folder (communication).
  • On-demand chaining; needs only for "can't run without": a module may turn on the add-on it chains to when it needs it (ActivateModule, e.g. job_search turns cv on at the CV step); the core still asks that module's access card, and the start shows as ModuleStateChanged. job_search's needs is []. Why: forcing every start through the Hub hindered more than it helped, and the state events keep it visible (modules).
  • Turning a module off by hand is never refused: the modules that need it stay on, and the reply names them; with_dependents turns them off too, after a card. needs is start order only, and a needed module that fails doesn't stop its needers. Why: you can always turn something off (modules).
  • An off module isn't started by a call: a call to a tool of an off module answers not_available, naming the module. The agent asks you, and on your yes runs modules.on. Only a module marked start_on_use (the page opener) starts when used. Why: nothing turns on without you (modules).
  • modules.add loads a new module from its package and turns it on, after your Allow on a card (in Auto too). Why: it runs new code (modules).
  • modules.remove(settings = keep | purge) takes a module out of this run, after your Allow on a card (in Auto too). It is never refused: the modules that need it stay on, and the result lists them. purge deletes only config/<id>.toml and config/<id>.local.toml. It never deletes the module's folder or edits config/modules.toml; the result tells you to do that by hand. modules.add brings it back. Why: only your settings are deleted, and only when you say so (modules).
  • Pages open through IPageOpener: callers use open_page, and html_viewer provides the slot. Why: no core module names the viewer (modules).
  • The voice contract: IVoice with listen(session_id, destination) and finish(session_id, discard); VoiceDestination is talker or caller. Voice notes requires the contract, not voice_in's id. Why: any input can serve voice sessions (messaging).
  • Build it once: behaviour two parts need is one reusable part, listed in the index with who uses it (principle 13, reusable parts). What the main app and the independent apps share goes in app_kit (standard library only, never imports assistant), and each part has one import path. Why: a second copy drifts and is a bug.

Agents

  • The Agent Hub does coordination only: focus, tasks, messages and the access-list review. It holds no door, no names and no modes. The core knows agents only as callers (Callers, D2) and never starts their tasks. Why: what every module needs belongs in the core; the Hub can be off or reloaded without taking the door or the modes with it (agents).
  • Callers port (D2): the core holds the agent names, each caller's permission mode, who is you ([core.permissions] you) and who relays your answers (relays). Why: one list, read by the gate, the handler and the modules alike (core).
  • Agent Hub contracts: ITaskAgent and the Hub's commands and events (agents).
  • Module agents' workspace: a module's agent works in modules/<id>/workspace/ (gitignored). An optional data_folder in config/<id>.toml, outside the repo, moves it there; the workspace is copied once, never moved or deleted. Your own documents stay where config names them. Why: your data stays out of the repo tree (agents).
  • Each module may edit its own folder: a module's agent gets a write grant on its module's folder by default; the task_agents helpers don't. Why: a module's agent maintains its own code, and the helpers are generic (agents).
  • Which CLAUDE.md loads: the repo's CLAUDE.md imports only the short overview. Module agents (repo_claude_md = false: cv's and the job agent) skip the repo's CLAUDE.md files (claudeMdExcludes) and load the short developer rules (infra/developer_rules.md) with their module's docs page. The Main Assistant, the Talker and the helpers load the repo's. Why: fewer tokens every turn, and no repo rules steering an agent that works on one module (agents).
  • Worker context and edit batching: the worker is reminded at 150k tokens (context_reminder) and hands off to a fresh session itself. Its prompt asks it to batch edits, and a hook adds a note on its second edit to a file, once per file. Neither interrupts it. Why: every step resends the whole conversation, so a large context and repeated edits make every step cost more, and an interrupt costs a full step (runtime).

Permissions

  • One permissions handler, part of the core: always on; no module or agent can turn it off or reload it. Every module asks through ctx.permissions, and the core fills in who is asking. Grants are saved in config/permissions.toml (yours, gitignored, protected), with an older data/permissions.toml copied once if that file is missing. Its grant calls (permissions.grants / grant / revoke) are on the core's menu. The reviewer and you come from [core.permissions]. Why: a module that grants permissions could be turned off or reloaded by an agent (permissions).
  • Grants per kind of agent: one grant per module and subject (helper_2 shares helper's). Why: a grant follows the job, not one session (permissions).
  • Only you set Auto: every session starts in Manual. SetPermissionMode to Auto is taken only from the core or a you caller; Manual is taken from anyone. Why: an agent must never lift its own cards (permissions).
  • One gate, in dispatch_tool (D4): a call is checked for its arguments and the item's callers, then an item marked ask shows you a confirm card first. The risky steps ask in Auto too: modules.add / remove / reload always, modules.off with dependents, and the Talker's restart. A you caller runs at once. Agents keep Claude Code's own asks. Why: one place checks every call, wherever it comes from (permissions).
  • No other menu item is marked risky: rezi.write_resume already follows your yes, hub.cancel and agents.close are your word or can be undone, and permissions.grant / revoke ask in their own code.
  • The Main Assistant's RELOAD: / ADD_MODULE: line asks on the agent's own permission card, shown in Auto too. Why: the Hub's held-question flow (pause, ask, resume on the answer) is built on that card (permissions).
  • The review is a listener (D6): before an access card shows, the core sends ReviewAccessList; the Hub's reviewer answers with AddCardNotes. With no Hub the router answers at once, and the card says "not reviewed". The handler may cancel a module's tasks when a revoke turns it off, but never starts one. Why: the core never starts a task (permissions).

Open decisions

  • Persistence technology.
  • UI handler: a part that owns the user-facing UIs (chat window, Quest, glasses), instead of each UI being its own module. Its shape isn't decided; the temp UI stands in.
  • Self-improvement permissions: how the Main Assistant gets access to its own code (plan); it will go through the permissions handler.
  • Parallel voice sessions: they need the voice service to take several listeners; today one session runs at a time.
  • Do the Talker's card answers count as yours? (G17) Today the Talker is a relay ([core.permissions] relays = ["talker"]): it may send AnswerPermission and AnswerPermissionRequest from an ALLOW / DENY in its reply, on any turn. It never sets Auto.
  • Moving the add-ons out of the repo: the module_folders mechanism is built, and the move itself is yours.
  • An add-ons folder's own rules: a CLAUDE.md per add-on, and a write grant on the add-ons folder for the Main Assistant that ends with its session (a new permissions feature).
  • Code versus data in the workspaces: the skills and scripts in cv's and the job agent's workspaces sit with your data; moving them into the module folder means deciding what in them is personal.
  • Whether the extension-marketplace note is superseded by module_folders (it says the loader takes no folder from config).
  • The core still names agents: core/callers.py reserves hub and talker, core/permissions/handler.py maps a talker: prefix to its pair's mode, and core/context.py lets any ITaskAgent provider send ReloadModule / AddModule (the card is asked in infra, so the core trusts the role, not your Allow).
  • Known gaps: "you" is trusted by module id, not by the folder the code came from; the "found in two folders" check runs only at startup, not on modules.add; the modules.add card doesn't show which folder the code comes from; the microphone request only logs and allows.
