Decisions

What's decided, what's still open, and what's deliberately deferred. Back to the overview.

Decided

  • Core and PC-side modules: Python.
  • Quest 3 client: separate Unity (C#) app, connecting through the gateway module.
  • Deployment: runs on a PC for now, a server later.

  • Agents: an Agent Hub module coordinates a Talker, a Main Assistant, and subagents. The core doesn't know agents exist.

  • Runtime module control: modules can be turned on and off while the app runs, through a core control interface; a control panel UI module and the Talker use it. A module's code can be reloaded, and a brand-new module added, while the app runs (decided 2026-11-03). Only changes to the core, contracts or shared helpers, and a new module that needs a new contract or port type, need a restart. See core.

  • Views: for now a throwaway temp UI (a local web page in its own window: Main Assistant left, Talker right) plus terminal 1. The UI configurations you'll actually want get their own design conversation. Terminal 2 (assistant_view) still exists but is off by default.
  • Agent runtime: claude -p sessions on the subscription (terms checked; built, see agent runtime).
  • Agent Hub contracts: ITaskAgent and the Hub's commands and events (built).
  • Independent apps where it pays off (decided in an earlier session, recorded 2026-10-27): a part may be its own app, deployed and run on its own, when it's useful without the assistant. It doesn't import the assistant; the main app launches it and talks to it through two-way hooks (its local HTTP API one way, its event stream the other), via a thin module. The modules inside the main app stay a modular monolith in one process. First one: the HTML viewer (src/html_viewer, run with python -m html_viewer); its thin module is html_viewer.
  • Permissions are per module: one permissions handler; every module asks through ctx.permissions, and the core fills in who is asking. Not the whole app holding everything. Grants are saved in data/permissions.toml, in the protected zone.
  • The permissions handler is part of the core (2026-11-05), not a module: always on, and no module or agent can turn it off or reload it. ctx.permissions is a PermissionsPort forwarding to it; the allow-all stand-in and the planned IPermissions contract are gone. Its grant calls (permissions.grants / grant / revoke) are on the core's menu beside modules.*. It stays generic: it uses only the router's send, the bus's publish and the container's get_one, and the shared contracts; the Main Assistant's review is a normal task; it imports no module and holds no module-specific logic, and the registry's special start order for IPermissions is gone. It names no agent: the reviewer (main_assistant) and you (temp_ui) are set in [core.permissions] of config/default.toml (2026-11-08). Why: a module that grants permissions could be turned off or reloaded by an agent. First piece built: access lists.
  • Grants are saved per kind of agent (2026-11-05): one grant per module and subject. helper_2 shares helper's grant; the job agent's subject is job_search_agent. A list can't start an agent in Auto: every session starts in Manual (permissions).
  • Build it once (2026-11-02): behavior two parts need is one reusable part, listed in the index with who uses it (principle 13, Reusable parts). What the main app and the independent apps share goes in a new package, app_kit (standard library only, never imports assistant); each part has one import path, so the window functions aren't re-exported from assistant.infra. This replaces the HTML viewer's own copy of the window code (viewer decision 8). The ctx.permissions stand-in is built now, ahead of the handler. app_kit and agent_tags are built (2026-11-02); the stand-in was built too, and replaced by the core's handler on 2026-11-05.
  • Worker context and edit batching (2026-11-03): every step resends the whole conversation, and the worker's context kept growing large while its code edits were poorly batched (the same file edited again and again), so every step cost more. The rule: the worker is reminded at 150k (context_reminder) and hands off to a fresh session by itself. Batching is a standing line in the worker's prompt plus a hook note on the second edit to a file, once per file, covering Edit, Write, MultiEdit and NotebookEdit, for the worker only. Neither interrupts it: an interrupt costs a full step and balloons the context. Grouping edits never means skipping the architecture-check, the tests or ruff. A restart with reset instructions goes with them. How it runs: runtime.
  • Module shape (2026-11-04): every module is a wrapper (manifest, lifecycle, context) with a menu of tools; the Talker and the Main Assistant find modules through a one-line directory, then open only the menu they need; the core finds modules by folder; modules chain through declared events and shared services with sessions and destinations (modules, principles 14 to 17). Dependencies stay by contract only: voice_in gets a voice contract, and voice notes requires that contract, not voice_in's id. The overview now draws the core with its ports. Mostly planned; the build plan is the module-shape change note, with voice notes built first.
  • How the agents call module tools (2026-11-05): through one MCP server in front of the core, with three fixed tools (list modules, show a menu, use an item). Not an MCP server per module: those would go around the permission check, the directory, the links between modules and hot swap. Modules never speak MCP; an outside tool with its own MCP (Unity) becomes a module that is an MCP client. Why: modules. Build plan: the module system change note.

Open decisions

  • Persistence technology
  • UI handler: a separate part that owns the user-facing UIs (chat window, Quest, glasses) instead of each UI being its own ad hoc module. Its shape isn't decided; the temp UI is a throwaway stand-in until it is.
  • Self-improvement permissions: how the Main Assistant gets access to its own code (plan); will go through the permissions handler
  • How general event types are: one general event (for example a text stream carrying its source and destination) reused by voice, notes and transcription, or a new type per use. Fewer types mean fewer restarts; too few make events vague (modules).
  • The voice contract's shape: decided 2026-11-05 (module system, chunk 6): IVoice with listen(session_id, destination) and finish(session_id, discard); VoiceDestination is talker or caller (messaging). Parallel sessions stay open: they'd need the voice service to take several listeners.

Deliberately deferred

Don't add more architectural machinery until two or three very different modules (e.g. a text input, a browser tool, and a view) are built and we've checked that each can be replaced independently. Let those real modules show which abstractions are actually missing.
