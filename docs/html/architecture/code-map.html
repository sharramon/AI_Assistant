How it reads

  • Imports point one way. Modules import contracts, infra and app_kit; infra imports contracts and app_kit; the core imports contracts, infra and app_kit (merge, module_docs). No module imports another module, and the core imports no module. app_kit and the independent apps (voice_service, html_viewer, cv_tool) never import assistant. Tests sit apart: the test kit (assistant.testkit) holds the fakes they share, may import anything, and is imported by tests only, the central tests/ and each module's own tests/.
  • Module folders. The loader finds modules by folder: the repo's src/assistant/modules/ first, then each outside folder [core] module_folders names (add_module_folders); every module's app/ folder goes on the import path (add_app_folders).
  • The door and the gate. The core opens the DoorServer (in its CoreDoor) before any module starts. Each door call becomes the core's own ListModules, GetMenu or InvokeTool, with the caller its token proves; InvokeTool goes through dispatch_tool, the one gate (the item's callers, then a confirm card for items that ask first). A module asks for a door config through its ModuleDoor, only for itself or an agent it claimed in Callers.
  • Agents. Every big agent is a ProfileAgent (its AgentProfile, ClaudeSession and SessionTaskAgent), built through AgentKit; it claims its id from the core's Callers port. The Agent Hub starts their tasks through ITaskAgent. Messages between agents and from modules go through the Hub's Delivery (DeliverMessage, never into a turn), and an agent's message to one that isn't its child asks first through the MessageGate. More in Agents: code layout.
  • SHOW tags. The worker and the Talker both open a SHOW tag's page with one helper, show_page, through the page-opener slot (IPageOpener); the core starts the module that provides it if it's off (StartProvider).
  • Independent apps. Each runs in its own process, launched by its thin module through CompanionApp, and refuses other hosts and other origins with local_guard (companion app checklist).
  • The permissions handler is part of the core; it asks you through cards (PermissionRequested), reads each agent's mode from Callers, and asks the Hub's Reviewer to review an access list (ReviewAccessList, answered with AddCardNotes), so the core never starts a task.

Known gaps

Where the code doesn't follow principles 18 to 22 yet, cleaned up in small chunks and redrawn here when each lands:

  • The Agent Hub split (not approved): the Hub's module still does several jobs.
  • Facts as text: the Hub writes "permission allowed" / "permission denied" as free text in TaskUpdated.text.
  • temp_ui is a stand-in until the UI handler is designed.
  • The core still names agents in three spots: the reserved ids hub and talker in core/callers.py, the talker: prefix in the permissions handler, and any ITaskAgent provider may send ReloadModule / AddModule (core/context.py).
