The core idea: agents and modules

Messages go through the Agent Hub; tools go through the module door. You talk to the agent with the focus, other agents' questions wait behind a ! on their tab, and every agent sends one-line milestones to the Main Assistant. More in Agents: big agents and their modules.

Summary

A highly modular personal AI assistant that serves as a long-term experimental platform. A small, stable core hosts an ever-changing set of independent modules (inputs, outputs, views, tools, background workers, and the AI orchestration itself) that can be added, replaced, or discarded with minimal changes elsewhere.

The agents reach every module through one MCP door with three fixed tools, not an MCP server per module. That keeps every caller behind the core's checks and the agents' context small (why not plain MCP?).

The style is a modular monolith using ports & adapters, dependency injection, and event-driven communication. The modules run in one process. Changing a module's code needs no restart: the module is reloaded in place (turned off, given its new code, turned on), and a brand-new module is added the same way (reloading). Changes to the core, contracts or shared helpers, and a new module that needs a new contract or port type, still need a restart. Turning modules on and off also happens while the app runs (runtime module control: built in the core; a control panel and asking the Talker come later). Independent deployment is, for parts that are useful on their own: such a part is its own app that the main app launches and talks to through two-way hooks, via a thin module (decisions). The HTML viewer is the first.

The core runs on a PC today and will later move to a server, so it must not assume a local desktop: configuration, secrets, and data paths come from config files and environment variables, and user-facing interfaces are modules or remote clients. Headsets (Quest 3) and smartglasses are remote clients that connect over the network.

Currently fixing

Making modules truly self-contained: each module's code, companion app, defaults, tests, docs and dependency list live in its own modules/<id> folder. Beside them sit a core group (the host and the core modules), config/ (your choices only) and generated/. Dependencies are declared per module, and removing a module asks whether to purge its settings or keep them. The plan: module folders. Progress: 13 of 20 done, item by item in the checklist docs/next-steps/module-folders-checklist.md, each checked against the code.
