Module library

This page lists every module, what it does and its interface: the tools on its menu, the commands it handles and sends, and the events it publishes and listens to. Each name links to the module's own docs. The data types are listed below the tables, with links to their API entries. What a module is, and how it is found and reached, is on modules. Back to the overview.

Generated: scripts/build_docs.py rewrites the tables between the library:start and library:end markers. It reads each module's Manifest (description, contracts, handles, sends, publishes, listens) and its Menu without starting the module, and takes the group from the module's docs.toml. "On" is the default on-list in config/modules.toml. To change a row, change the module's manifest or menu, not the table. tests/test_module_docs.py fails when the tables are stale or a module has no docs. The data types below are written by hand.

Module pages

Every module keeps its docs in its own folder, src/assistant/modules/<id>/docs/, next to its code and tests, so a module's docs move with it. The main docs hold only the app-wide pages: this architecture, the agents docs, the API reference (the core only) and the principles.

Each module's folder has three standard pages, first and in this order, and a docs.toml (module_docs):

Page Sections
README.md, its overview Purpose (and its status: on by default, off by default, or planned), Wrapper (its manifest), Config (its settings: the defaults in its module.toml, which your config/<id>.toml overrides; configuration), Code and tests (paths only)
architecture.md Interface (tools, commands it handles and sends, events it publishes and listens to), Owns and launches (processes, windows, ports, files, companion apps), Inner workings (one diagram and a few lines), Planned
tools.md Its menu, generated from the module's own Menu by the docs build; notes go after the generated part

Other pages are optional. A module that launches its own app keeps that app's full design in its folder: the voice service in voice_in, the HTML viewer app in html_viewer, and the job project in job_search.

Groups. The group in docs.toml decides whether a module is core or an add-on (the core line). Core modules are what the app can't start without: agent_hub, talker, main_assistant, task_agents, usage, voice_in, temp_ui, console_io and assistant_view. Add-ons are every other module: cv, job_search, html_viewer, voice_notes, and the echo_orchestrator stand-in. The docs list the core modules' tabs first, then the add-ons', and the tables below use the same split.

The core (the host, not a module) handles AnswerPermissionRequest, AddCardNotes, SetPermissionMode, InvokeTool, ListModules, GetMenu, ActivateModule, StartProvider, DeactivateModule, ReloadModule, AddModule, RemoveModule, ShutdownRequested (the module control commands among them; InvokeTool goes to the module whose menu has the item). It provides IAgentNames, IModuleDoor, offers its own menu as core (modules.list, modules.menu, modules.docs, modules.on, modules.off, modules.reload, modules.add, modules.remove, permissions.grants, permissions.grant, permissions.request, permissions.revoke), and publishes ModuleStateChanged, PermissionRequested, PermissionChanged.

What the generated tables don't show yet:

  • The core's own side. Besides the line above, the core handles GetMenu, StartProvider, ShutdownRequested, SetPermissionMode, AnswerPermissionRequest and AddCardNotes. Its menu, under the id core, holds modules.list, modules.menu, modules.docs, modules.on, modules.off, modules.reload, modules.add and modules.remove, plus permissions.grants, permissions.grant, permissions.request and permissions.revoke. It also publishes the cards, PermissionRequested and PermissionChanged (core, modules). The generator doesn't write this yet.
  • job_search listens to ModuleStateChanged once. Its manifest lists the event twice (once through the agents' shared list), so the row shows it twice.
