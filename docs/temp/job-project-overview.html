2. How a job gets handled

StepWhat happens
Startstart_job.cmd → next_job.ps1: cd C:\Chang\Jobs\CV, read next_prompt.txt (fallback: a fixed "Next job…" prompt), run claude.exe "<prompt>" in an interactive window. No loop.
InputsThe prompt; QUEUE.md's top row and "Next session" note; the job's own doc if half done; auto_apply.md form defaults; answer_bank.md; the tailored CV (.odt for text, .pdf to upload); the posting in Chrome; the 3-per-company cap from the log / Sheet.
Workapply-session + fill-application: Claude fills every field in Chrome; you tick consent boxes / CAPTCHAs and press Submit.
OutputsThe application doc (<date>_<company>_<role>.md), a Google Sheet row, applications_log.md, auto_apply.md Done table, QUEUE.md updated, a new next_prompt.txt.
Hand-offhandoff.ps1 opens the next session's window and kills the current one. Same idea as this assistant's "fresh session per task + HANDOFF note".

A job search run

  1. company-sweep: sync the registry (company_boards.json) from the StartUp / UnderRadar docs; run sweep.py --days 14 with JobRadar's Python (10–15 min, every tracked board + Indeed + keyword queries); fix failed boards; web searches; Chrome-only boards (Meta, Google, Apple…); detect_ats.py / discover.py for new companies.
  2. linkedin-job-pass: recommended feed + keyword searches, read-only, under 10 min, 8–20 s gaps.
  3. Screen against job_criteria.md (H-1B sponsorship, mid level, no contract, caps), then job-list-compile builds the 50/30/20 list → new QUEUE.md rows.
  4. Log the run in job_criteria.md §6. Rule from CLAUDE.md: confirm with you before running any search.

A search run is long, mostly HTTP + web search, and touches Chrome only for some boards and LinkedIn. Applying is short per job but needs Chrome on your logged-in profile and your hand on Submit.

What's in .claude

Only skills/ (7 skills, three with Python scripts). No settings.json, agents, commands or .mcp.json; the folder isn't a git repo. Permissions come from your user-level Claude settings.

JobRadar (C:\Chang\Git_projects\Resume)

A separate code project: a Streamlit job discovery and fit-scoring app with its own docs. The job project only borrows its .venv (it has jobspy) to run the sweep scripts and reads its data\jobs.db as leads; it never edits it. It's a data source, not part of the per-job flow.

Cloud agents vs local

A cloud agent runs on a remote machine with a git checkout. It can't see C:\Chang\Jobs\CV (not a git repo), your .odt CVs, JobRadar's venv, or your logged-in Chrome (LinkedIn, the Sheet, application forms). It adds: runs while the PC sleeps, no local CPU, many in parallel. Its status comes back by polling a session API, not through ReportTask, so it needs its own ITaskAgent adapter. Uploading job data to the cloud is "sending outside the machine". Possible later for the web-only half of a search (web searches + board APIs), with results written back locally.
Recommendation. Start local: a job_agent module built from SessionTaskAgent + ClaudeSession, working in C:\Chang\Jobs\CV, fresh session per job (keeps the one-job-per-session idea, drops handoff.ps1). Add StartTask.agent_id and multi-task tracking in the Talker so "is the job search still going?" is a GetTaskStatus on the job agent. Talk between agents only through the Hub. Leave cloud agents for a second step, for search runs only.
